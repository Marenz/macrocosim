** B. Browser-driven UI tests

The Rust integration tests in =tests/= cover the HTTP and gRPC
boundaries but stop at the JSON shape — none of them exercise the
SPA. The metrics panel, the topology canvas's drag / connect
gestures, the REPL's autocomplete + electric-pair + rainbow
overlay, and the chart-update path through the WebSocket are all
unverified by anything other than manual smoke. The plan below
turns that into automated coverage.

Tool choice: *Playwright* (Node, headless Chromium / WebKit /
Firefox, auto-wait built in, native screenshot diff). It's the
default for projects without a JS framework — the alternative
(Cypress) is Chrome-mostly and heavier; Selenium is verbose. One
=playwright.config.ts= + a =tests-browser/= directory.

Determinism is the real pain. The topology graph layout is
seeded but not reproducible across machines (font metrics,
vis-network's animation timing); the physics tick + history
sampler push WS frames continuously; consumer-curve / cloud-curve
animations move power around at 200 ms. Tests need to either
freeze the world at known points or assert on stable structure
rather than pixel-exact screenshots.

*** TODO U1. Unload/drop a loaded microgrid from memory      :rust:design:

Counterpart to on-demand loading (the config.lisp-dissolution
track, discussed 2026-07-23): drop a registered microgrid and its
runtime without touching its files on disk — load brings it back.

The enabler is a per-mg runtime-handle bundle plus a symmetric
=microgrid_unregistered= event, mirroring how dynamic ADD already
works end to end (=make-microgrid= → =microgrid_registered= → the

  physics + sampler JoinHandles, loopback abort} per mg id,
  populated in both spawn sites (boot loop and the registered-event
  arm — near-identical code, could unify while at it). On
  unregistered: trigger the gRPC shutdown FIRST — in-flight
  telemetry stream tasks hold component Arcs and would keep
  streaming a frozen site; killing the transport ends them — then
  abort the rest and drop the bundle.
- Lib: =(unload-microgrid ID)= under the interpreter lock — guard
  against a running scenario (v1: refuse; D7's per-mg scenario
  scope is the real fix), remove the registry entry, clear
  =current_microgrid= if it points there, emit unregistered. WS
  forwarders need nothing: last site Arc drops → event Sender
  closes → the forwarder's =RecvError::Closed= arm exits.
- Wrappers: =DELETE /api/mg/{id}=, a macroctl verb, a UI button.
- Ports rebind on re-load; the make-microgrid port-collision check
  errors cleanly if something else took the port meanwhile.

Open decisions: drop the mg's dispatches on unload (with Deleted
events so streams + UI update) vs. keep them for the next load;
and whether unload-by-script (a script may register several mgs)

** P. Physics realism upgrades

The electrical layer is deliberately behavioral (no power flow, no
losses) — see the architecture notes in AGENTS.md. The two items
below are the cheapest upgrades that a downstream control app's own
accounting would actually notice; island-mode frequency coupling
(swing equation) was considered and deferred — not needed while
every scenario runs grid-tied.

*** TODO P1. Battery round-trip efficiency + idle draw             :fidelity:

Today charging and discharging both move SoC at 100 % efficiency and
an idle battery holds SoC forever. A control app that schedules
charge/discharge cycles and audits the energy balance sees numbers a
real site never produces. Add to =BatteryConfig=:

- =:efficiency-pct= (round-trip, default ~92): apply √η on each leg —
  charging stores =P·dt·√η=, discharging draws =P·dt/√η= — so a full
  cycle loses the configured fraction and the loss is visible on
  whichever leg the app measures.
- =:idle-draw-w= (default a few W): constant self-discharge +
  BMS/electronics draw integrated every tick regardless of setpoint,
  so SoC sags slowly over a long soak run.

Both default-off-able for configs that want the old ideal behaviour
(=:efficiency-pct 100 :idle-draw-w 0=). SoC integration stays in
=Battery::tick=; the meter aggregation path is untouched (losses are
internal to the battery, the inverter still reports commanded AC).

Bounds caveat (from the 2026-06-04 review): the gateway's AC∩DC bounds
intersection in =aggregate_child_bounds= is only numerically correct at
η=1. Once efficiency lands it must account for the conversion, or the
setpoint gate validates against mismatched AC-side and DC-side envelopes.

*** TODO P2. Battery voltage-vs-SoC curve                          :fidelity:

=dc_voltage_v= is a constant from config, so =dc_current_a=
(= apparent/V) never varies with state of charge — real packs sag
toward the bottom and rise toward the top of the SoC window, and
BMS dashboards key on exactly that. Replace the constant with a
simple piecewise-linear curve parameterised by (=:voltage-min=,
=:voltage-nominal=, =:voltage-max=) anchored at (soc_lower, 50 %,
soc_upper), keeping =:voltage-v= as the nominal for backward
compatibility. Telemetry-only change — power physics stays on W, so
no setpoint / bounds behaviour shifts.

** M. Modbus and CAN device interfaces

Goal: a microgrid can expose its components as raw devices instead
of through the Microgrid gRPC API — inverters, meters and EV
chargers over Modbus TCP (SunSpec-style register maps), batteries
over CAN (BMS-style frames). Only one of the two is available for a
given microgrid: either the gRPC API or the device interfaces.

The gRPC path adds the gateway's rules on top of the hardware:
bounds intersection, setpoint validation, request lifetimes,
augmentations, the gateway delay and ramp, the SoC window. None of
that exists on the device path, so the devices must protect
themselves the way real ones do (revert timeouts, their own limits).

Done as preparation (the 2026-10 polish, sub-projects 1-5):
- The UI reads a microgrid's data through an in-process copy of the
  Microgrid service, so it does not need the public gRPC port.
- One gateway per microgrid holds every API rule
  (=src/sim/gateway.rs=); the components are plain hardware.
- One startup path per microgrid (=MicrogridRuntimes=,
  =src/runtime.rs=); the interface choice goes there.
- The component trait is split into capability traits
  (=src/sim/component/=), so a register map can ask a component
  what it can do.
- Names and units are the same everywhere
  (=docs/names-and-units.md=), for the register maps to follow.

Still ahead, in this order:
1. The UI design pass (shared colour, type and spacing values; a
   light theme; a button and form kit; layout; one way to show
   server errors; the disagreeing component counts; the chart time
   zone).
2. The physics the device interfaces need (P1, P2 and M2-M6 below).
3. The interfaces themselves (M1, M7).

*** TODO M2. Device-level protections                       :fidelity:design:

Without the gateway a raw setpoint never expires: the components
have no watchdog or revert timer of their own. Real devices do —
SunSpec controls carry a revert timeout and ramp time
(=WMaxLimPct=, =RvrtTms=, =RmpTms=), BMSes drop to safe limits when
the heartbeat stops, chargers fall back to a safe current. Model
these in the components (or a per-device layer under the
interface), not in the gateway.

*** TODO M3. Battery over CAN                                   :fidelity:

Typical BMS frames (e.g. SMA/Pylontech 0x351/0x355/0x356/0x359) need:
- charge and discharge voltage limits, and charge and discharge
  current limits in amps;
- pack voltage that follows SoC and current (see P2);
- signed current, temperature, state of health;
- lowest and highest cell voltage and temperature, with cell ids;
- alarm and warning bits, contactor state, charge/discharge request
  flags, and a heartbeat with timeout behaviour.

Today only SoC, power and a fixed voltage exist.

*** TODO M4. Inverter over Modbus                               :fidelity:

SunSpec models 1/120/121/122/123/124/160/70x/802 need:
- an operating state (off, sleeping, starting, MPPT, throttled,
  fault, standby) and event bit fields;
- separate DC and AC sides: PV string voltage and current at the
  maximum power point, the battery DC side;
- heatsink temperature with derating;
- monotonic lifetime energy counters, with scale factors;
- apparent power and power factor, line-to-line voltages, signed
  per-phase currents;
- controls with their own revert timeout and ramp time,
  connect/disconnect, and power-factor or volt-var modes (M2).

*** TODO M5. Meter over Modbus                                  :fidelity:

SunSpec 201-204 or vendor maps need:
- genuinely unbalanced per-phase values: signed current, apparent
  power, power factor;
- line-to-line voltages;
- separate import and export energy registers, per phase, plus
  reactive energy by quadrant.

Today the energy total is net only, and reaches history and the UI
but not the telemetry stream.

*** TODO M6. EV charger over Modbus                             :fidelity:

Vendor maps (Alfen, ABB, Keba, Phoenix-style) need:
- the IEC 61851 states A-F (only cable states are modelled today);
- setpoints in amps per phase, and actual per-phase currents;
- session energy and total energy, the hardware current limit,
  error codes;
- a fallback current when the controller goes quiet (M2).

*** TODO D8. Deterministic clock-sync with the app under test          :testing:

E2E with an external app is necessarily real-time + wall-clock (the app is a

tolerance and a run costs minutes. A shared virtual-time contract —
macrocosim's stepped clock advancing in lockstep with the app — would make E2E
fast and bit-reproducible, but needs the app to honour an external tick. Worth it
only if a consumer opts in; the absolute-schedule live-cue gap (J-era) belongs
here too.

** d1. Rethink ~file-exists-p~ resolving against the config's load dir :design:lisp:

The current =defuns::fs::register= (=src/lisp/defuns/fs.rs=) resolves
relative paths in =(file-exists-p PATH)= against the config file's
load directory (the same base =(load PATH)= uses). The motivation
was to keep =load-overrides='s gate

#+begin_src elisp
(when (file-exists-p "microgrids/config.7.overrides.lisp")
  (load "microgrids/config.7.overrides.lisp"))
#+end_src

answering the same question both halves of that =when= ask — the
two used to disagree when the process CWD differed from the config
dir, which broke the override-replay path inside
=remove_persisted_override= and the test that exercises it.

That's still a real coordination problem, but the fix is a little
heavy-handed:

- *Emacs divergence.* Real Elisp's =file-exists-p= resolves against
  =default-directory=, not the load path. Anyone porting code from
  Emacs (or eyeballing the docstring) would expect CWD-relative
  resolution; ours quietly rebases.
- *Surprises for non-override paths.* =(file-exists-p
  "telemetry.csv")= etc. now also rebases — fine if the user
  always means "next to config.lisp" but wrong if they meant CWD.
- *Coupling to =load_dir= at registration time.* The closure
  captures the path on =Config::new=, so a later =set_load_path=
  on the ctx (if we ever expose one to Lisp) wouldn't be visible
  to =file-exists-p=. =(load PATH)= in tulisp reads =ctx.load_path=
  on every call.

*Better directions to consider:*

1. Drop the special handling in =file-exists-p= and instead change
   the Lisp side: =load-overrides= in =sim/common.lisp= could build
   an absolute path before the gate, eg. by exposing the
   override-file path as a Rust-side defun (=(overrides-path)=
   already exists; make it return an absolute path).
2. Land a tulisp-level fix: add a =ctx.load_path= getter (currently
   =pub(crate)=) so a closure can resolve at call time, mirroring
   =(load PATH)=.
3. Push a =file-exists-p= change upstream into tulisp itself,
   matching =(load)='s resolution.

(2) or (3) is probably the right answer; (1) is the smallest patch
on the macrocosim side.

*Where the workaround lives today:* =defuns::fs::register= closes
over =load_dir: PathBuf=, propagated from =Config::new= via
=defuns::register_runtime=. The matching test
(=ui::tests::persisted_remove_drops_form_immediately=) inlines a
local =load-overrides= defun and relies on this resolution to find
the override file.

** d2. Promote per-mg override file into the per-mg config file :design:lisp:ui:

Currently every successful eval lands in the per-microgrid override
file (=microgrids/config.<id>.overrides.lisp=). The next step in
that flow: a UI action that takes the override file's contents and
folds them into the matching =microgrids/config.<id>.lisp= (inside
the =:topology= lambda — see below), then empties the override
file. After the action the world is unchanged but the source-of-
truth has shifted from "runtime edit" to "canonical microgrid
config" and the entry is no longer editable from the UI overrides
dialog.

*Where it'd land:* a button in the chrome (probably called Persist
or Promote), a server-side endpoint that does the file munging, and
an entry in this UI dialog that confirms the move.

*Open questions to settle before coding:*

- Where in =microgrids/config.<id>.lisp= does the content go? The
  natural slot is inside the =(make-microgrid :topology (lambda
  () …))= lambda body, alongside whatever topology the file
  already declares. Insertion point: before the trailing
  =(load-overrides)= call, so the canonical forms run first and
  then any remaining overrides layer on top. Mechanical append at
  the end of the lambda is the floor — semantic grouping (collect
  rename-component calls near the renamed components, etc.) is
  much harder and probably not worth automating in v1.
- Does the action try to dedup against existing forms in the
  per-mg config file? eg. if the override is
  =(rename-component 1 "alpha")= and the config already calls
  =(rename-component 1 "main-grid")= inside the topology, do we
  replace the existing call, append after it, or just append at
  the end and let last-write-win semantics carry the day?
- Does the action run =tulisp-fmt= over the merged file, or
  preserve the existing whitespace / comments verbatim and only
  format the appended block?
- After the move, the override file is empty and the per-mg config
  file grew. Reloading should yield the same microgrid (same
  forms, just relocated). Worth a test that round-trips
  add → promote → reload → state-equal.

*Why deferred:* the immediate-write override file makes the
override file the pending log. Promote-to-config is a one-way
commit gate on top of that, but the design questions above need a
real config sample to test against — easier to settle once a heavy
microgrid config has accumulated some real overrides.

** d3. Parallel-paths share semantic — does this match real installs? :design:fidelity:

We currently model "child shared by N parents" as "each parent sees
1/N of the child's flow" (parallel-conductor semantic). It's
physically real for high-current buses split into N cables for
ampacity, each with its own CT and meter, summed by an upstream
aggregator. But that's an unusual SCADA-level topology.

The more common multi-parent setup in real microgrids is *redundant
observers* — two meters on the *same* wire (Class A + Class B,
primary + backup) both reporting the full flow, with the SCADA layer
deduping or selecting one. Under our current semantic, those two
meters would each read half, which isn't what the user expects.

If user feedback pushes us either way, options are:

- *Keep parallel-share as default*, document the redundant-observer
  use case as "express it via =:hidden t= on the backup meter so it
  doesn't appear in the connections graph".
- *Flip default to count-fully-per-parent*, and add an explicit
  =:share <fraction>= plist arg for the parallel-conductor case.
- *Add a topology-level kind annotation* (=:redundant-with <id>=,
  =:parallel-with <id>=) so the connection graph itself encodes
  intent. Most expressive, most invasive.

** d4. Per-phase reactive setpoints                         :design:reactive:

The proto's =SetElectricalComponentPower= takes a single scalar
=power= value, not per-phase. Real inverters can be commanded to
dispatch unbalanced reactive across phases for voltage support. Out
of scope for v1; would need a proto extension or a side-channel
defun. Tracked here so we don't forget the gap.

** d5. Per-source attribution under MxN                     :design:fidelity:

Done in essence (2026-08-21): an inverter publishes its own push
scaled by each battery's =dc_accept_ratio= (accepted / pushed from
the battery's last tick), so a clip at the SoC envelope shows on the
inverter and the meters above it, and M inverters on one bus split
the clip in proportion to what each pushed. What is left is only the
exotic case of a battery that would clip *asymmetrically* per source,
which a single ratio cannot express; revisit if it ever matters.

** d5b. Re-clamp an armed active setpoint as the envelope tightens  :design:fidelity:

The battery's bounds narrow with SoC, and the gateway gates *new*
setpoints against them — but a setpoint accepted earlier keeps its
ramp target while the envelope closes underneath it; only the
published power follows the clip (d5). The reactive path already
re-clamps its target to the live envelope every tick. Open question
whether the active path should do the same (honour-until-TTL today
vs silently shrinking an accepted command); decide with a real
controller in the loop.

Update (2026-08-24): the reactive path's own-envelope re-clamp described
above is now codified generically in =PowerAxis= (re-clamps every tick,
shared by both the active and reactive axes) rather than being
reactive-specific logic. The open question this entry tracks is
unchanged: whether an armed active setpoint should follow the same
re-clamp when a battery's SoC-derated envelope narrows, or honour the
command until TTL as it does today.

Adjacent, and now symmetric on both axes: the wall-clock vs tick-clock
TTL asymmetry. Telemetry and the setpoint/augment gates sample the
envelope at =Utc::now()= (no site clock on a gRPC/UI thread) while
=PowerAxis::step= judges augmentation liveness on the tick clock, so a
scenario running on a scaled or frozen clock can see an augmentation
expire in one and not the other. Worth fixing once, for both axes,
alongside whatever this entry settles on.

Update (2026-10-04): resolved by the per-microgrid gateway. The
gateway now re-clamps a battery inverter's running command every step
to its share of the battery's SoC-throttled room, so the output
narrows as the window closes and climbs back at the ramp rate as it
reopens; the battery itself only clips at 0 % and 100 %. The
wall-clock / tick-clock asymmetry is gone too: lifetimes,
augmentations and every bounds read run on the site clock.

** d6. Persist-gate follow-ups (origin gating, form splitting) :design:lisp:

The core landed 2026-06-12: =Config::eval= persists a source to the
per-mg overrides file only when it moved the enterprise structural
fingerprint (register / connect / disconnect / remove / rename, plus
registry inserts) or contains a top-level =(setq *-defaults …)= —
so transient pokes no longer resurrect as config on reload. Settled
policy: defaults edits persist, renames persist, persistence is
origin-blind (REPL == canvas).

Deferred refinements, pick up if the need shows:
- *Origin gating (old option D)*: make the REPL scratch-by-default so
  structural experiments don't litter the overrides file. Needs an
  origin flag on the eval endpoints AND a visible "scratch — won't
  survive reload" indicator in the REPL, or it's a silent trap.
- *Form splitting (old option F)*: a mixed eval (one structural form +
  one poke) persists whole today; splitting top-level forms and
  persisting only the ones that moved the fingerprint closes that.
- *Net-zero edits*: an add+remove in one eval bumps the counter twice
  and persists despite changing nothing; a structure hash (old option
  A) layered on the counter would suppress it.
